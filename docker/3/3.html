1. Controlar los recursos de un contenedor (CPU, memoria)

Por defecto, un contenedor puede usar toda la CPU y toda la memoria de la máquina. El problema es evidente: un solo contenedor que se desmadre —una fuga de memoria, un proceso disparado— puede tumbar el servidor entero y llevarse por delante a los demás. En un servidor de verdad esto no vale, así que les ponemos límites.

Los dos que usarás casi siempre van en el docker run:

ParámetroPara qué sirve
--memory (-m)Memoria máxima que puede usar el contenedor.
--cpusNúcleos (o fracción) que puede usar.

Por ejemplo, un contenedor limitado a medio núcleo y 256 MB:

docker run -d --name limitado --memory 256m --cpus 0.5 nginx

Aquí hay una diferencia de fondo que conviene entender bien, porque no se comportan igual. La memoria es un límite duro: si el contenedor intenta pasarse, Docker lo mata en el acto — es el famoso OOM (out of memory), y lo verás como un contenedor que muere con código de salida 137. La CPU es un límite blando: no lo mata, simplemente lo frena para que no pase de su cuota. Uno es una pared; el otro, un freno.

Para ver el consumo en vivo de lo que está corriendo:

docker stats

Nos muestra, contenedor a contenedor, cuánta CPU y memoria gasta en tiempo real. Es lo primero que mirarás cuando algo vaya lento.

Existe una imagen en DockerHub llamada polinux/stress, pensada justo para forzar a un contenedor a consumir recursos. Le ponemos un límite de 128 MB y le pedimos que intente reservar 200 —más de lo permitido— para ver cómo Docker lo corta:

docker run --rm -it --memory 128m polinux/stress stress --vm 1 --vm-bytes 200M

El --vm 1 --vm-bytes 200M es simplemente "arranca un proceso que intente ocupar 200 MB". Al pasarse de los 128, Docker lo mata con el OOM que acabamos de ver.

2. Reducir el tamaño de las imágenes con Multi-stage

Cuando construimos una imagen, muchas veces necesitamos herramientas para preparar la aplicación —compiladores, librerías de desarrollo, paquetes que solo hacen falta durante la construcción— que después, para ejecutarla, no usamos para nada. Si lo dejamos todo en la misma imagen, acabamos arrastrando cientos de megas de cosas que en producción sobran.

El multi-stage lo resuelve partiendo el Dockerfile en dos fases:

  1. En una primera fase, con todas las herramientas, construimos la aplicación.
  2. En una segunda fase, que empieza limpia y vacía, copiamos únicamente el producto ya terminado de la primera. Todo lo que hizo falta para construir se queda fuera de la imagen final.

La clave que lo hace posible es que podemos tener varios FROM en un mismo Dockerfile; cada uno abre una etapa.

FROM golang:1.22 AS build
WORKDIR /app
COPY . .
RUN go build -o miapp

FROM alpine
COPY --from=build /app/miapp /miapp
CMD ["/miapp"]

La primera línea, FROM golang:1.22 AS build, abre una etapa y le pone nombre: build. Ese nombre nos hará falta luego. Aquí usamos la imagen oficial de Go —un lenguaje que se compila: escribimos código y una herramienta lo convierte en un único fichero ejecutable, el binario—. Esa imagen de Go trae todo el kit de compilación, que son cientos de megas. Con COPY . . metemos nuestro código dentro (el primer punto es "todo lo de mi carpeta", el segundo es "a la carpeta de trabajo de la imagen") y con RUN go build lo compilamos: obtenemos el binario miapp.

Un segundo FROM alpine abre una etapa nueva, mínima y vacía. Y con COPY --from=build /app/miapp /miapp copiamos, desde la etapa build, solo el binario ya compilado. El kit de Go, el código fuente y todo lo demás se quedan en la primera etapa, que se descarta. La imagen final es un alpine diminuto con un único binario dentro.

El resultado lo vemos al mirar docker images: la misma aplicación que pesaba, por ejemplo, 800 MB en una sola etapa, baja a apenas 15-20 MB.

3. Distroless: qué es y cuándo usar

Con alpine hemos llegado a una imagen pequeña. Se puede ir un paso más allá con distroless.

Distroless es una familia de imágenes base que publica Google (bajo gcr.io/distroless/) a las que se les ha quitado todo lo que no es imprescindible para ejecutar nuestra aplicación. No hay gestor de paquetes, no hay shell, no hay ls, ni cat, ni bash. Solo la aplicación y las librerías justas para arrancar.

No existe una única imagen distroless, sino varias: cada lenguaje necesita cosas distintas para funcionar. Si nuestra app es un binario ya compilado (como el de Go del ejemplo anterior) no necesita nada más, y usamos gcr.io/distroless/static. Si es una app de Java, necesita la máquina virtual de Java para ejecutarse, así que hay una imagen distroless que la incluye. Solo tenemos que elegir la que corresponda a lo que vayamos a ejecutar.

Existe incluso un paso más extremo: la imagen scratch, que está literalmente vacía — cero ficheros. Solo sirve para binarios totalmente autónomos, y por eso distroless suele ser la opción más práctica.

Esto da dos ventajas. La primera, tamaño: son aún más pequeñas que alpine. La segunda, y la importante, seguridad: si un atacante se cuela dentro, se encuentra un sitio vacío — no hay shell que abrir, no hay herramientas con las que moverse, no hay gestor de paquetes para instalar nada.

Se usan como cualquier base, típicamente como etapa final de un multi-stage:

FROM golang:1.22 AS build
WORKDIR /app
COPY . .
RUN go build -o miapp

FROM gcr.io/distroless/static
COPY --from=build /app/miapp /miapp
CMD ["/miapp"]

¿Cuándo usarla? En producción, para aplicaciones ya compiladas y estables. ¿Cuándo no? Mientras desarrollamos y depuramos, porque esa misma falta de shell hace que no podamos entrar con docker exec ... sh a cotillear — no hay sh que ejecutar.

4. Preparar un contenedor para producción

Ya sabemos limitar recursos y adelgazar la imagen. Falta el paso principal: que el contenedor se comporte como un servicio serio, profesional y seguro.

No ejecutar como root

Por defecto, el proceso dentro del contenedor corre como root. Si alguien se cuela, es root dentro del contenedor — un riesgo innecesario. En el Dockerfile podemos crear un usuario y cambiar a él con USER:

RUN useradd -r appuser
USER appuser

Un concepto importante es tener en cuenta que pondremos el RUN y el USER antes del CMD.

Configuración por variables de entorno

Una imagen debe ser inmutable y reutilizable: la misma imagen tiene que valer para desarrollo, preproducción y producción. La configuración no va dentro de la imagen — se inyecta desde fuera al arrancar, con variables de entorno.

Por ejemplo: el MARIADB_ROOT_PASSWORD, el WORDPRESS_DB_HOST… son variables que la imagen lee al arrancar. Nunca metas una contraseña o una URL dentro de la imagen; se pasa por fuera.

Esta idea es la base de los ConfigMaps y Secrets de Kubernetes.

Healthcheck

Que un contenedor esté "corriendo" no significa que la aplicación funcione. El proceso puede estar vivo pero la app colgada, sin responder a nadie. Docker, por defecto, solo sabe si el proceso vive, no si la aplicación responde. Un HEALTHCHECK cubre justo esa diferencia — le enseña a Docker cómo preguntarle a la app si está realmente viva. Es una instrucción más del Dockerfile, que se suele poner cerca del final, junto al CMD.

La comprobación depende del tipo de servicio: a una web se le pide una página, a una base de datos se le hace un ping, y a cualquier otra cosa se le comprueba como tenga sentido:

# Web (nginx, apache, una API…)
HEALTHCHECK CMD curl -f http://localhost/ || exit 1

# MariaDB / MySQL
HEALTHCHECK CMD mariadb-admin ping -h localhost || exit 1

# PostgreSQL
HEALTHCHECK CMD pg_isready -U postgres || exit 1

# Redis
HEALTHCHECK CMD redis-cli ping || exit 1

La lógica es siempre la misma: un comando que devuelve éxito si todo va bien, y el || exit 1 que marca el contenedor como enfermo si falla.

Con esto, docker ps ya no dice solo "Up", sino "Up (healthy)" o "(unhealthy)".

Política de reinicio

Ya vimos --restart en la Clase 1; en producción es donde cobra sentido. Con --restart unless-stopped, si el contenedor se cae o reinicias el servidor, vuelve a levantarse solo. Es lo que convierte un contenedor en un servicio que no tienes que vigilar.

.dockerignore

Un fichero hermano del .gitignore: lista lo que no queremos que entre en la imagen al construir. Sin él, un COPY . . se traga todo el directorio — engorda la imagen y puede colar dentro cosas que no deberían estar, como esas credenciales que justo acabamos de decir que van por fuera.
